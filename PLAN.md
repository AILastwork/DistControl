# План разработки C++-утилиты ограниченного доступа к USB-токенам

## 1. Цель

Сделать собственную C++-утилиту на базе примера `DKCLHelper` из статьи
DistKontrol, которая показывает пользователю только назначенные ему USB-токены
и не позволяет через наш интерфейс подключать остальные устройства.

Исходные условия проекта:

- ОС пользователей: Windows 10.
- Токены могут иногда переставляться между портами.
- Требуется поддержка доменных групп Active Directory.
- `dkcl64.exe` запускается через подготовленную регистрацию службы `dkclient`.
- Нужен журнал событий для службы безопасности.
- Подготовлен скриптовый установщик/zip-пакет с установкой нашего клиента,
  политики доступа и регистрацией `dkcl64.exe` как службы.
  MSI/EXE-мастер можно сделать следующим этапом.

Основная модель первой версии:

```text
Пользователь Windows -> наша C++-утилита -> \\.\pipe\dkclient -> DistKontrolUSB Client
```

Модель установки:

```text
Windows 10
├─ служба DistKontrolUSB Client (dkcl64.exe -n --config=...)
├─ наша пользовательская GUI-утилита
├─ allow.json
└─ журнал подключений и отказов
```

Ограничение строится не по 16 группам концентратора, а по отдельным устройствам
вида:

```text
SERVER-Gr-N.PORT
```

Например:

```text
OFFICE-HUB-Gr-1.3
OFFICE-HUB-Gr-2.14
```

## 2. Что берём из статьи производителя

Из статьи и исходника `DKCLHelper` используем:

- подключение к локальному каналу `\\.\pipe\dkclient`;
- отправку команд `LIST`, `DEVICE INFO`, `USE`, `STOP USING`;
- парсинг списка устройств;
- парсинг полей `NICKNAME`, `IN USE BY`, `PRODUCT`;
- общую интерфейсную идею: список устройств, обновление, подключение,
  отключение.

Что меняем:

- не показываем все устройства из `LIST`;
- добавляем политику доступа по пользователям Windows;
- повторно проверяем право перед каждой командой `USE`;
- добавляем журналирование подключений и отказов;
- убираем автоподключение всего, что пользователь не должен видеть.
- добавляем административный сценарий переназначения токена, если его
  переставили в другой порт.

## 2.1. Выбор технологии интерфейса

Рекомендуемый стек для проекта: **C++ / WinAPI / Win32 UI или WTL**.

Причины:

- целевая ОС — Windows 10;
- нужна работа со службами Windows;
- нужен установщик, права на файлы, Program Files и ProgramData;
- нужна интеграция с доменными пользователями и группами;
- не нужно тащить GTK runtime и MSYS2-библиотеки на каждое рабочее место;
- проще собрать переносимый EXE/MSI под корпоративную среду.

GTK-4/MSYS2 подходит как пример производителя и быстрый прототип, но для
внедрения на Windows 10 он менее удобен:

- потребуется распространять GTK DLL;
- сложнее сопровождать установку;
- внешний вид менее нативный для Windows;
- больше зависимостей.

Qt тоже возможен, но для простой утилиты он избыточен:

- больше размер поставки;
- отдельные вопросы лицензирования/развёртывания;
- ради таблицы, кнопок и настроек его преимущества небольшие.

Итоговое решение:

```text
Прототип логики можно делать на PowerShell/C++ консоли.
Рабочую версию делать на C++ с нативным Windows UI.
```

## 3. Политика доступа

Файл политики хранится отдельно от штатного клиента, например:

```text
C:\ProgramData\DiskControl\allow.json
```

Пример:

```json
{
  "assignments": [
    {
      "users": ["DOMAIN\\ivanov", "ivanov"],
      "groups": [],
      "devices": [
        {
          "endpoint": "OFFICE-HUB-Gr-1.3",
          "nickname": "BANK-KEY-01",
          "product": ""
        }
      ]
    },
    {
      "users": [],
      "groups": ["DOMAIN\\Бухгалтерия"],
      "devices": [
        {
          "endpoint": "OFFICE-HUB-Gr-2.8",
          "nickname": "REPORT-KEY-01",
          "product": ""
        }
      ]
    }
  ]
}
```

Правила:

- если пользователь не найден в политике, доступ запрещён;
- один пользователь может иметь 1, 32, 64 и более токенов;
- один токен можно назначить нескольким пользователям;
- назначение возможно по имени пользователя, SID или группе Windows;
- `endpoint` обязателен;
- `nickname` и `product` используются как справочная информация или
  дополнительная проверка.

Так как токены могут переставляться, первую рабочую версию лучше строить так:

- доступ проверять по `endpoint`;
- `nickname` показывать пользователю и администратору;
- при перестановке токена администратор обновляет `endpoint` в политике;
- в административном режиме должен быть список всех найденных USB-токенов,
  чтобы выбрать новый `endpoint` без ручного поиска в JSON.

## 4. Архитектура C++-приложения

### 4.1. Модули

`IpcClient`

- подключение к `\\.\pipe\dkclient`;
- отправка команд;
- чтение ответа;
- обработка ошибок канала.

`DkCommandService`

- `listDevices()`;
- `getDeviceInfo(endpoint)`;
- `useDevice(endpoint)`;
- `stopUsingDevice(endpoint)`.

`DeviceParser`

- парсинг `LIST`;
- парсинг `DEVICE INFO`;
- нормализация статусов `NO ONE`, `YOU`, другой пользователь.

`UserContext`

- получение текущего пользователя Windows;
- получение SID;
- проверка членства в группах Windows.

`PolicyManager`

- чтение `allow.json`;
- проверка прав пользователя;
- проверка доменных групп Active Directory через Windows API;
- режим deny-by-default.

`DeviceAccessService`

- получение полного списка устройств;
- обогащение через `DEVICE INFO`;
- фильтрация по политике;
- повторная проверка перед `USE`.

`AuditLogger`

- успешные подключения;
- отказы;
- ошибки канала;
- попытки подключения запрещённых устройств.

`AdminTool`

- полный список USB-токенов;
- поиск по `nickname`;
- назначение токена пользователю или группе;
- обновление `endpoint`, если токен переставили;
- экспорт текущего списка токенов в CSV/JSON.

`MainWindow`

- список доступных пользователю токенов;
- кнопки `Подключить`, `Отключить`, `Обновить`;
- статус подключения;
- сообщение, если пользователю ничего не назначено.

## 5. Алгоритм работы

1. Запуск приложения.
2. Получение текущего пользователя Windows.
3. Загрузка политики доступа.
4. Если назначений нет — показать пустой список и отказ.
5. Проверить доступность `\\.\pipe\dkclient`.
6. Если канал недоступен — предложить запустить DistKontrolUSB Client.
7. Выполнить `LIST`.
8. Для каждого устройства выполнить `DEVICE INFO,<endpoint>`.
9. Отфильтровать устройства по политике.
10. Показать пользователю только разрешённые токены.
11. Перед `USE` повторно выполнить `DEVICE INFO`.
12. Повторно проверить `endpoint`, `nickname`, `product`.
13. Если правило совпало — отправить `USE,<endpoint>`.
14. Если правило не совпало — отказать и записать событие в журнал.

Если токен переставили:

1. Администратор открывает режим настройки.
2. Нажимает `Обновить полный список USB`.
3. Находит токен по новому `nickname`/`product`.
4. Выбирает новый `endpoint`.
5. Сохраняет политику.
6. Пользователь после обновления видит токен уже по новому адресу.

## 6. Этапы реализации

### Этап 1. Прототип C++

- использовать основу `DKCLHelper` по IPC-командам;
- вынести IPC в отдельный класс;
- сделать минимальный нативный Windows-интерфейс;
- вывести список устройств из `LIST`;
- вывести поля из `DEVICE INFO`.

### Этап 2. Политика доступа

- добавить `allow.json`;
- добавить определение пользователя Windows;
- реализовать фильтрацию устройств;
- реализовать deny-by-default;
- добавить повторную проверку перед `USE`.

### Этап 3. Журналирование

- писать лог в `C:\ProgramData\DiskControl\logs`;
- фиксировать пользователя, endpoint, действие, результат;
- отдельно писать отказы доступа.
- предусмотреть CSV/JSON лог или запись в Windows Event Log.

### Этап 4. Установка

- подготовить каталог `C:\Program Files\DiskControl`;
- политику хранить в `C:\ProgramData\DiskControl`;
- дать обычным пользователям права только на чтение;
- изменение политики разрешить только администраторам.
- установить `dkcl64.exe`;
- зарегистрировать службу `dkclient`;
- настроить автозапуск службы;
- проверить, что команда `LIST` из службы возвращает список USB.

Статус: скриптовая установка подготовлена в `install.cmd` /
`installer\Install-DiskControl.ps1`. Реальная проверка службы `dkclient` должна
быть выполнена на тестовом ПК из консоли администратора.

### Этап 4.1. Установщик

Подготовлен переносимый zip-пакет через `build-installer.cmd`.
Он включает:

- копирование нашей GUI-утилиты;
- копирование `dkcl64.exe`;
- создание каталогов:
  - `C:\Program Files\DiskControl`;
  - `C:\ProgramData\DiskControl`;
  - `C:\ProgramData\DiskControl\logs`;
- настройку ACL:
  - пользователям чтение и запуск;
  - администраторам изменение;
- регистрацию службы `dkclient`;
- запуск службы;
- создание ярлыка нашей утилиты на рабочем столе или в меню Пуск;
- опциональную проверку канала `\\.\pipe\dkclient`.

Отдельный MSI/EXE-мастер с графическим интерфейсом установки остаётся
опциональным следующим этапом.

### Этап 5. Строгая защита

Если требуется исключить обход штатным клиентом:

- сделать Windows-службу `DiskControlService`;
- запускать службу от отдельной учётной записи;
- перенести работу с `\\.\pipe\dkclient` в службу;
- пользовательский GUI должен общаться только со службой;
- служба проверяет права перед каждой командой.

## 7. Риски и ограничения

- В опубликованном примере нет `VID`, `PID` и серийного номера USB.
- Надёжный идентификатор из доступных данных — `endpoint`.
- `nickname` и `product` являются дополнительными проверками, но не заменяют
  физический серийный номер.
- Если пользователь имеет прямой доступ к штатному клиенту и его настройкам,
  он может обойти клиентскую утилиту.
- Для защиты от обхода нужна отдельная защищающая Windows-служба
  `DiskControlService` и ограничения прав на файлы.

## 8. Контрольные вопросы перед разработкой

1. Какая версия Windows используется у пользователей?  
   Ответ: Windows 10.

2. Токены всегда стоят в постоянных портах или могут переставляться?  
   Ответ: могут иногда переставляться.

3. Требуется ли работа с доменными группами Active Directory?  
   Ответ: да.

4. Нужно ли скрывать штатный DistKontrolUSB Client от пользователя?  
   Ответ: отдельное окно клиента скрывать не требуется, так как `dkcl64.exe`
   будет работать как служба.

5. Нужен ли журнал для службы безопасности?  
   Ответ: да.

6. Требуется ли установщик MSI/EXE?  
   Ответ: скриптовый установщик и zip-пакет уже подготовлены; MSI/EXE-мастер
   можно сделать поверх них, если нужен привычный мастер установки.

7. Будем оставаться на GTK-4/MSYS2 или выбрать Qt/WinAPI?  
   Рекомендация: выбрать нативный Windows UI на C++/WinAPI. GTK оставить как
   референс из статьи производителя, но не как основной стек внедрения.
